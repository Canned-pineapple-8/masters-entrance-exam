### 1. Понятие триггера

Триггером называется особый вид хранимой процедуры, автоматически запускаемой сервером базы данных в ответ на наступление определённого события, связанного с изменением данных в конкретной таблице (или представлении). Принципиальное отличие триггера от обычной хранимой процедуры состоит в способе его активации: обычная процедура вызывается явно, по запросу пользователя или прикладной программы, тогда как триггер запускается неявно, самой СУБД, всякий раз при попытке выполнения над связанной с ним таблицей операции соответствующего типа — вставки, изменения или удаления данных.

Все действия, выполняемые триггером, рассматриваются как часть той же транзакции, в рамках которой было выполнено вызвавшее его срабатывание действие. Отсюда следует важное практическое следствие: если в теле триггера обнаруживается нарушение целостности данных или иная ошибка, это может привести к откату всей транзакции целиком, включая и исходную операцию, инициировавшую срабатывание триггера.

### 2. Классификация триггеров

**По моменту срабатывания относительно события.** Триггер `BEFORE` запускается непосредственно перед выполнением связанного с ним события (например, до фактической вставки записи), что позволяет, в частности, проверить и при необходимости скорректировать вставляемые значения ещё до их записи в таблицу либо отменить операцию целиком. Триггер `AFTER` запускается после того, как событие уже полностью выполнено, и применяется, как правило, для действий, зависящих от уже окончательно зафиксированных значений, — аудита изменений или обновления связанных, производных данных в других таблицах. Триггер `INSTEAD OF` («вместо») запускается вместо самого события, то есть исходная операция (вставка, изменение, удаление) фактически не выполняется вовсе, а вместо неё выполняется код, заданный в теле триггера; такие триггеры определяются, как правило, только для представлений (в частности, для представлений, не допускающих прямого обновления в обычном порядке) и должны определяться на уровне строки.

**По типу события.** Различают триггеры, реагирующие на операции `INSERT`, `UPDATE` и `DELETE`; один и тот же триггер может быть объявлен реагирующим сразу на несколько типов событий одновременно. В ряде СУБД (в частности, в Microsoft SQL Server) дополнительно поддерживаются DDL-триггеры, реагирующие не на изменение данных, а на изменение структуры базы данных (`CREATE`, `ALTER`, `DROP`), — однако такая возможность реализована далеко не во всех системах: например, в PostgreSQL поддерживаются исключительно DML-триггеры.

**По уровню срабатывания.** Строчный триггер (объявляется конструкцией `FOR EACH ROW`) запускается однократно для каждой отдельной строки, затронутой вызвавшей его операцией, — то есть если оператор `UPDATE` изменяет сразу сто строк, строчный триггер сработает сто раз. Табличный (операторный) триггер (объявляется конструкцией `FOR EACH STATEMENT`) запускается лишь однократно на весь оператор целиком, независимо от числа фактически затронутых им строк. Триггеры типа `INSTEAD OF`, как отмечалось выше, обязаны быть строчными; триггеры уровня `BEFORE` и `AFTER`, определяемые для представлений, напротив, обязаны быть табличными (это конкретное правило может отличаться в разных СУБД).
### 3. Доступ к изменяемым данным внутри триггера

Внутри тела триггера, как правило, доступны специальные псевдозаписи (переходные переменные), позволяющие обратиться к значениям строки до и после выполнения вызвавшей триггер операции: `OLD` содержит значения строки до изменения (доступно для операций `UPDATE` и `DELETE`), а `NEW` — значения строки после изменения (доступно для операций `INSERT` и `UPDATE`). Именно через обращение к этим переменным тело триггера получает возможность анализировать и, в случае триггеров `BEFORE`, даже корректировать вставляемые или изменяемые значения.

### 4. Назначение триггеров

Триггеры применяются для решения нескольких характерных задач, которые затруднительно или невозможно реализовать средствами исключительно декларативных ограничений целостности, рассмотренных ранее.

**Поддержание сложных ограничений целостности.** Триггер способен проверять условия, охватывающие сразу несколько таблиц или требующие нетривиальных вычислений, — то есть такие ограничения, которые выходят за пределы возможностей простых декларативных ограничений (`CHECK`, внешних ключей) и требуют процедурной логики проверки.

**Аудит изменений.** Триггер, срабатывающий после (`AFTER`) каждой операции изменения данных в контролируемой таблице, может автоматически заносить сведения о произведённом изменении (кто, когда и что изменил) в отдельную служебную таблицу журнала аудита.

**Автоматическое поддержание производных (агрегированных) данных.** При изменении данных в одной таблице триггер может автоматически пересчитывать и обновлять связанные, производные значения в другой таблице (например, суммарную стоимость заказа при изменении состава позиций заказа), избавляя от необходимости пересчитывать всю сводную информацию заново при каждом обращении к ней.

**Реализация обновляемых представлений.** Триггеры типа `INSTEAD OF`, определённые для представления, позволяют корректно интерпретировать операции вставки, изменения и удаления, адресованные представлению, транслируя их в соответствующие операции над базовыми таблицами, на которых это представление построено, — даже в тех случаях, когда представление само по себе не является напрямую обновляемым.

### 5. Пример синтаксиса

Общая (упрощённая) схема создания триггера в диалекте PostgreSQL состоит из двух частей: функции триггера, содержащей его логику, и собственно оператора `CREATE TRIGGER`, связывающего эту функцию с конкретным событием и таблицей.

```sql
CREATE OR REPLACE FUNCTION check_salary_increase()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.Зарплата < OLD.Зарплата THEN
        RAISE EXCEPTION 'Зарплату нельзя понижать';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_check_salary
BEFORE UPDATE ON Сотрудники
FOR EACH ROW
EXECUTE FUNCTION check_salary_increase();
```

Приведённый триггер срабатывает перед каждым изменением строки таблицы `Сотрудники` (уровень `FOR EACH ROW`, момент `BEFORE`) и сравнивает новое значение зарплаты (`NEW.Зарплата`) со старым (`OLD.Зарплата`); если новое значение оказывается меньше прежнего, выполнение прерывается с ошибкой, что автоматически приводит к отмене (откату) вызвавшей триггер операции обновления, — тем самым реализуется сложное ограничение целостности, которое затруднительно выразить простым декларативным ограничением `CHECK`, поскольку оно требует сравнения нового значения со старым, а не проверки одного лишь нового значения по отдельности.
