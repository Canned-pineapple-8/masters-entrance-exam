### 1. Понятие инкапсуляции

Инкапсуляцией в объектно-ориентированном программировании называется объединение данных (состояния объекта) и методов, оперирующих этими данными, в единую сущность — класс, — сопровождаемое ограничением (сокрытием) прямого доступа к внутренним деталям реализации этой сущности извне. Инкапсуляция, таким образом, содержит два взаимосвязанных, но различных аспекта: во-первых, собственно объединение данных и связанного с ними поведения в единый программный модуль; во-вторых, сокрытие информации (information hiding) — предоставление внешнему коду доступа лишь к строго определённому, явно объявленному открытому интерфейсу класса, тогда как детали внутренней реализации остаются скрытыми и недоступными напрямую. Хотя формально инкапсуляцию можно рассматривать и без сокрытия информации, на практике в языке C++ полноценной инкапсуляцией принято считать именно сочетание обоих названных аспектов.

### 2. Модификаторы доступа в C++

Управление видимостью членов класса (полей и методов) в C++ реализуется посредством трёх модификаторов доступа.

**`public`** — член класса, объявленный с этим модификатором, доступен без ограничений из любого внешнего по отношению к классу кода.

**`private`** — член класса доступен исключительно из методов самого этого класса (а также, при отдельном явном разрешении, из объявленных дружественными функций и классов, рассмотренных ниже); попытка обратиться к такому члену извне класса приводит к ошибке компиляции.

**`protected`** — член класса доступен из методов самого класса и из методов классов, производных от него посредством наследования, но недоступен из произвольного стороннего кода, — то есть занимает промежуточное положение между `public` и `private`.

Существен синтаксический нюанс, специфичный для C++: уровень доступа по умолчанию (то есть применяемый к членам, для которых явно не указан ни один из модификаторов) различается для ключевых слов `class` и `struct` — по умолчанию `private` для `class` и `public` для `struct`, при том что содержательно эти две конструкции языка идентичны и отличаются лишь этим умолчанием.

### 3. Пример класса с инкапсуляцией

```c++
class BankAccount {
private:
    double balance;

public:
    BankAccount(double initialBalance) : balance(initialBalance) {}

    double GetBalance() const {
        return balance;
    }

    void Deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    bool Withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
            return true;
        }
        return false;
    }
};
```

В этом примере поле `balance` объявлено закрытым (`private`) и потому недоступно для прямого изменения извне класса — обратиться к нему можно лишь через открытые методы `GetBalance`, `Deposit` и `Withdraw`. Именно благодаря этому ограничению класс `BankAccount` способен гарантировать соблюдение своего внутреннего инварианта (в частности, невозможность образования отрицательного баланса при снятии средств методом `Withdraw`): любое обращение к состоянию объекта неизбежно проходит через контролирующую его корректность логику метода, а прямая, бесконтрольная запись в поле `balance` из внешнего кода (что было бы возможно, объяви класс это поле как `public`) попросту невозможна.

### 4. Функции доступа: геттеры и сеттеры

Для предоставления контролируемого доступа к закрытым полям класса используются специальные методы доступа: геттеры (называемые также аксессорами) — методы, возвращающие текущее значение закрытого поля (в примере выше — `GetBalance`), и сеттеры (называемые также мутаторами) — методы, устанавливающие новое значение закрытого поля, зачастую с дополнительной проверкой его корректности перед фактическим изменением (в примере выше эту роль частично выполняет метод `Deposit`). Наличие подобных методов доступа позволяет встроить в саму точку изменения или чтения данных произвольную дополнительную логику — проверку допустимости значения, вычисление производных величин, логирование обращений, — не будучи ограниченным простым, бесконтрольным присваиванием.

При этом методы доступа рекомендуется предоставлять лишь тогда, когда внешнему коду действительно необходима возможность читать или изменять соответствующее поле, — а не автоматически, по умолчанию, для каждого закрытого поля класса; в частности, следует избегать геттеров, возвращающих неконстантную ссылку на внутреннее поле-член, поскольку это фактически предоставляет внешнему коду прямой доступ к изменению внутреннего состояния объекта в обход самого класса, тем самым сводя на нет содержательный смысл инкапсуляции.

### 5. Модификатор `friend`

В отдельных случаях, когда некоторой внешней функции или другому классу действительно требуется прямой доступ к закрытым членам класса (например, для реализации эффективной операции, требующей одновременного доступа к внутреннему состоянию сразу нескольких взаимодействующих классов), C++ предоставляет модификатор `friend`, позволяющий явным образом объявить конкретную функцию или класс «дружественными» — то есть предоставить им доступ к закрытым и защищённым членам, минуя обычные ограничения инкапсуляции. Поскольку подобное объявление всякий раз ослабляет инкапсуляцию класса, использовать его рекомендуется лишь в действительно обоснованных случаях, а не как общее средство обхода модификаторов доступа.

### 6. Практическое значение инкапсуляции

Инкапсуляция обеспечивает ряд существенных практических преимуществ при разработке программ. Во-первых, она защищает внутренние инварианты объекта, гарантируя, что его состояние изменяется только предусмотренным, контролируемым образом, — что существенно упрощает поиск ошибок, поскольку круг кода, способного нарушить корректность состояния объекта, ограничивается методами самого класса. Во-вторых, она снижает связанность (coupling) между различными частями программы: внешний код взаимодействует с классом исключительно через его открытый интерфейс, не полагаясь на конкретные детали внутренней реализации, — а значит, эта внутренняя реализация впоследствии может быть свободно изменена (например, из соображений повышения эффективности) без необходимости вносить какие-либо изменения во весь код, пользующийся данным классом, при условии сохранения неизменным самого открытого интерфейса.
