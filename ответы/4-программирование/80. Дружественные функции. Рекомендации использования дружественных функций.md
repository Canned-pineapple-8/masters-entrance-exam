### 1. Понятие дружественной функции

Дружественной функцией называется функция, не являющаяся членом класса, однако наделённая прямым доступом к его закрытым (`private`) и защищённым (`protected`) членам — в этом отношении она пользуется теми же правами доступа, что и обычный метод самого класса, хотя формально таковым не является. Для предоставления функции статуса дружественной её прототип объявляется внутри тела класса с предшествующим ключевым словом `friend`, тогда как её фактическое определение (реализация) размещается вне тела класса, как у обычной, самостоятельной функции.

```c++
class Auto {
    friend void SetPrice(Auto& car, double price);
private:
    std::string name;
    double price;
};

void SetPrice(Auto& car, double price) {
    car.price = price;   // прямой доступ к закрытому члену через дружественную функцию
}
```

### 2. Разновидности дружественных сущностей

Статус дружественной может получить не только самостоятельная (свободная) функция, но и метод другого, уже существующего класса, а также класс целиком — в последнем случае дружественными по отношению к данному классу становятся сразу все методы объявленного дружественным класса.

```c++
class Engine;   // предварительное объявление

class Car {
    friend class Engine;   // весь класс Engine объявлен дружественным классу Car
private:
    double fuelLevel;
};
```
### 3. Существенные свойства и ограничения дружественности

**Односторонность (несимметричность).** Дружественность не является взаимным отношением: класс или функция не могут объявить себя другом какого-либо класса самостоятельно, — решение о предоставлении доступа к своим закрытым членам всегда принимает исключительно сам класс, в определении которого и должно содержаться соответствующее объявление `friend`. Соответственно, если класс `A` объявляет дружественным класс `B`, это ни в коей мере не наделяет класс `A` встречным доступом к закрытым членам класса `B`.

**Нетранзитивность.** Дружественность не обладает свойством транзитивности: если класс `A` является другом класса `B`, а класс `B`, в свою очередь, является другом класса `C`, из этого никоим образом не следует, что класс `A` также является другом класса `C`, — каждое отношение дружественности должно быть объявлено отдельно и явно.

**Ненаследуемость.** Производные классы не наследуют дружественных функций своего базового класса: если некоторая функция объявлена дружественной по отношению к базовому классу, она не получает автоматического доступа к закрытым членам, добавленным уже в производном классе, — дружественность, объявленная для базового класса, не распространяется на его наследников.

**Дополнительные синтаксические ограничения.** Дружественные функции не могут объявляться с ключевыми словами `static` или `extern`. Существен также нюанс, отмеченный ранее применительно к перегрузке операторов: место объявления дружественной функции внутри тела класса (в секции `public`, `private` или `protected`) не имеет никакого значения для её статуса, — поскольку дружественная функция не является членом класса, обычные спецификаторы доступа, регулирующие видимость именно членов класса, к ней попросту не применимы.

### 4. Рекомендации по использованию дружественных функций

Поскольку предоставление статуса дружественной функции (или класса) фактически расширяет круг кода, имеющего беспрепятственный доступ к внутренней, закрытой реализации класса в обход его собственного открытого интерфейса, каждое такое объявление ослабляет инкапсуляцию класса, рассмотренную в одном из предыдущих вопросов, — а значит, применять этот механизм следует обдуманно и в ограниченном числе случаев, придерживаясь следующих общих рекомендаций.

**Использовать дружественные функции лишь при действительной необходимости.** Прежде чем прибегать к `friend`, стоит удостовериться, что стоящая задача не может быть решена посредством уже имеющегося открытого интерфейса класса (методов доступа, рассмотренных в вопросе об инкапсуляции) либо посредством обычной внешней функции, не требующей прямого доступа к закрытым членам (рассмотренной в вопросе о перегрузке операторов), — оба этих подхода сохраняют инкапсуляцию класса в неприкосновенности и потому предпочтительнее дружественной функции всюду, где они принципиально применимы.

**Прибегать к дружественности в оправданных случаях тесной содержательной связи.** Классические оправданные сценарии применения `friend` включают реализацию операторов, левый операнд которых не относится к типу самого класса (в частности, `operator<<` для вывода объекта в поток, рассмотренный в вопросе о перегрузке операторов), а также ситуации, когда два (или более) класса совместно реализуют единую, неразрывную логическую абстракцию, и предоставление им взаимного прямого доступа к внутреннему состоянию друг друга существенно упрощает и делает более эффективной их совместную реализацию, не оправдывая при этом искусственного раздувания открытого интерфейса каждого из этих классов ради нужд лишь одного конкретного «соседа».

**Ограничивать область предоставляемого доступа минимально необходимой.** Там, где реального доступа к закрытым членам класса требует лишь одна конкретная функция (или метод) другого класса, предпочтительно объявлять дружественной именно эту функцию, а не весь класс целиком, — объявление дружественным целого класса предоставляет доступ ко всем без исключения его методам, что, как правило, избыточно и увеличивает область кода, потенциально способную нарушить внутренние инварианты класса, предоставившего дружественный доступ.

**Документировать и обосновывать причину дружественности.** Поскольку каждое объявление `friend` представляет собой сознательно допущенное исключение из общих правил инкапсуляции, целесообразно сопровождать подобные объявления пояснением, почему обычные, не нарушающие инкапсуляцию средства (открытый интерфейс, внешняя функция) в данном конкретном случае оказались недостаточны, — это существенно облегчает последующее сопровождение кода и понимание границ, в пределах которых внутреннее состояние класса действительно может быть законно изменено кодом, формально находящимся вне самого класса.
